# 記憶の棚卸し

## 大原則

**勝手に消さない。** 記憶はユーザーが積み上げた資産で、消えたことに気づくのは
それが必要になった瞬間 — つまり手遅れになってからになる。
このskillでやるのは**提案までで、削除と統合は必ず承認を取ってから**実行する。

## 手順

### 1. 材料を出す

```bash
~/.kiro/bin/kiro-memory doctor
```

重複候補・更新が古いもの・description が長いものが機械的に列挙される。
これは**候補**であって、判断はここからが仕事。

### 2. 重複候補を精査する

候補として挙がったペアの**本文を両方 read する**。slug が似ているだけで
中身が別物のことは多い(`consumer-app-1812-...` と `consumer-app-1846-...` は
同じアプリの別課題であって、統合してはいけない)。

本当に同じ事実を指していた場合のみ統合する:

- 新しい方に情報を寄せて `kiro-memory add` で上書き(内容を失わないこと)
- 古い方を `kiro-memory rm` で消す
- 統合したことをユーザーに報告する

### 3. 古い記憶を確認する

更新が古い記憶は、**古いから消すのではない**。長く変わらない事実ほど価値が高い。
確認するのは「まだ正しいか」だけ:

- 参照しているファイル・パス・コマンドがまだ存在するか
- 手順が今のやり方と食い違っていないか

食い違っていたら**消すのではなく更新する**(`kiro-memory add` で上書き)。
その事実自体が消滅していた場合(廃止されたツールの手順など)だけ、
ユーザーに確認したうえで `rm` する。

### 4. 長い description を短くする

description は索引に載って毎セッション読まれる。80文字を超えるものは、
**本文はそのままに description だけ**短くする。

- 削るのは修飾・背景・言い訳。残すのは「何についての記憶か」が分かる語
- 固有名詞・コード値・数値は残す(検索の手がかりになる)
- 短縮した結果、何の記憶か分からなくなったら短くしすぎ

短縮も上書きなので、本文を read してから `kiro-memory add` し直すこと
(本文を渡し忘れると中身が消える)。

### 5. 報告する

やったことを列挙して報告する。「3件統合、2件更新、5件のサマリを短縮」のように。
消したものがあれば必ず明示する。
